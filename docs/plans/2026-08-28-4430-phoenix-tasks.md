# Phoenix tasks

> **Task #4430**, epic #310. A recurring task with no schedule: when it reaches
> Done it creates a fresh Backlog copy of itself, and the recurrence flag moves
> to that copy. Nothing runs the copy — the human dispatches it when they want
> to. This is the deliberately smaller replacement for the generic scheduling
> primitive removed by task #4407 (migrations v88/v90); see
> `docs/plans/2026-08-27-4407-revert-scheduled-tasks.md`.

**Goal:** Add `Task.phoenix: bool` and the respawn-on-Done behaviour, exposed
through the MCP tools, the task editor, the TUI creation form, and the card.

**Verify command:** `cargo fmt --check && cargo test && ./scripts/check-doc-paths.sh`

**Spec:** written and validating clean. `PhoenixRespawn` and the `== Phoenix ==`
prose in `docs/specs/tasks.allium`; the field, `respawn_failed` and the
"Phoenix marker" rendering section in `docs/specs/core.allium`;
`PhoenixIsNeverChained` on `AutoDispatchNextSubtask` in `docs/specs/epics.allium`;
the tool fields in `docs/specs/mcp-task-tools.allium`; cross-references on
`PrMerged` and `ExitSession` in `docs/specs/pr-workflow.allium`.

## The five decisions the spec encodes

1. **A Boolean, not a `TaskTag`.** `tag` already selects the dispatch prompt
   (`DispatchMode::for_task`) and marks review work (`TaskTag::is_review`).
   Phoenix has nothing to say about either, and a recurring *chore* is the
   ordinary case.
2. **Every route into Done respawns.** The trigger is the status transition, so
   `ConfirmDone`, `EditTask`'s STATUS section, `ExitSession`'s rebase/done
   branches and `PrMerged` all reach it.
3. **The flag is the receipt.** It is cleared exactly when the successor row is
   created. So it fires once, a Done→Review→Done round-trip cannot duplicate,
   and a *failed* respawn is a Done task still carrying the flag —
   `Task::respawn_failed`, rendered as a red `⚠` card indicator.
4. **Done outranks the respawn.** A failed respawn does not roll the transition
   back. A transient DB error must not block completing a task.
5. **Phoenix tasks are never auto-dispatched.** `AutoDispatchNextSubtask` skips
   them, which both closes the infinite-chain loop and is what the flag means.

## Global constraints

- Spec first, then tests, then code (`CLAUDE.md`).
- **Mutation boundary.** The respawn creates a task, so it goes through
  `TaskService`, never `state.db`. It lives in `src/service/tasks/crud.rs`
  beside the two status-writing funnels, not in a handler.
- **`OwnedTaskPatch` parity** and `patch_struct!` — read the `FieldUpdate`
  section of `docs/conventions.md` before touching `TaskPatch`.
- **Migration numbering.** v90 is the last registered migration; the new one is
  therefore v91 — but derive it from the last `MIGRATIONS` entry at execution
  time in case a sibling task lands one first. `ADD COLUMN` does not force
  SQLite to re-resolve the table's triggers, so the v90 hazard does not apply.
- `auto_run_plan` is the working template for the whole data path. Every file it
  touches (`git grep auto_run_plan`) except the TUI/editor/render ones needs the
  same edit for `phoenix`.

## Step 2 — The respawn itself

**Tests first** (`src/service/tasks/tests.rs`), one per spec clause:

- a phoenix task moved to Done gets a Backlog successor carrying the flag, and
  the predecessor's flag is cleared;
- the successor inherits title (verbatim), description, repo_path, tag, labels,
  base_branch, wrap_up_mode, epic, plan_path, auto_run_plan;
- the successor has no worktree, no tmux_window, no url, and `sort_order: None`;
- a **non**-phoenix task moved to Done spawns nothing;
- a task with `external_id` set spawns nothing even with the flag on
  (`FeedTasksAreExempt`);
- Done→Review→Done spawns exactly one successor in total (`TheFlagIsTheReceipt`);
- a no-op patch rewriting Done over Done spawns nothing;
- `close_session(Done)` respawns; `close_session(Review)` — the `pr` branch —
  does not;
- when the successor insert fails, the task is still Done and still carries the
  flag (`DoneOutranksTheRespawn`).

**Then:** one private `respawn_phoenix(&self, prior: &Task)` on `TaskService`,
called after the successful `patch_task` in **both** `update_task` and
`close_session`. It must:

- return early unless `prior.phoenix && prior.external_id.is_none()` and the
  write actually moved status *into* Done from something else;
- create the successor via the service's own create path;
- on success, clear `prior.phoenix` with a second patch;
- on failure, log at ERROR and return — never propagate an `Err` that would make
  `close_session`'s caller read the close as failed (see that method's doc
  comment on why its `Err` must mean exactly "the terminal write did not land").

## Step 7 — Card rendering

**Tests first** (`src/tui/ui/kanban/cards.rs` tests + a snapshot): a phoenix
Backlog card renders `♻`; a phoenix Done card renders `♻` *and* the
`⚠ respawn failed` indicator with the red state border; a non-phoenix card
renders neither; and a **width test** — a phoenix card's rendered line 1 is
exactly `col_width`, with a long title, so an under-reserved budget fails.

**Then:** the glyph on line 1 beside the message-flash glyphs, and a
`CardIndicator::RespawnFailed` variant fed by `Task::respawn_failed()` and
included in `state_border_color`'s RED arm.

> **The one real trap.** Every other card glyph (`▎ ✉ ➤ ▸ ✓ ⚠`) is a
> single-column BMP character, and `prefix_width` is built by *counting
> characters*. `♻` (U+267B) has emoji presentation in most terminals and is
> drawn **two** columns wide. Reserve its rendered width, not its `chars()`
> count, or every phoenix card overflows its frame by one column. This is the
> only place on the board where the two measures differ — it is written down in
> core.allium's "Phoenix marker" for the same reason.
