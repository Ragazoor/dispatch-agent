# 4706 — Audit of dispatch's skill and MCP tool descriptions

Scope: every description dispatch ships and can edit —
`plugin/skills/*/SKILL.md` frontmatter, `.claude/skills/*`, and the MCP tool +
parameter descriptions generated by `mcp_tools!` and `mcp_args!`.

Criteria: triggering, accuracy against the implementation, overlap between
surfaces, length/format, staleness.

Findings are ordered by severity within each section. Severity is about what an
agent does wrong as a result, not about how wrong the sentence is.

---

## A. Skill descriptions

### A1 — `.claude/skills/lint.md` never loads (blocker)

Claude Code discovers repo skills at `.claude/skills/<name>/SKILL.md`. A bare
`.md` file directly under `.claude/skills/` is not a skill directory, and `lint`
does not appear in this session's available-skills listing (`allium-weed-loop`
and `brainstorm-features`, its two siblings, both do).

The file's description — "Consult before wrapping up work in the dispatch repo —
explains custom Clippy lint rules…" — is well written and reaches nobody.

Resolved by deleting the file at the user's direction, rather than moving it to
`.claude/skills/lint/SKILL.md`.

### A2 — Two skills have no `name:` and no trigger clause

`plugin/skills/allium-loop/SKILL.md` and `.claude/skills/allium-weed-loop/SKILL.md`
both use a different frontmatter style from every other skill in the repo:
a quoted `description`, an `allowed-tools` array, and **no `name:` field**.

More importantly, neither description contains a "Use when…" clause. Both state
only what the skill does. A model choosing a skill autonomously has nothing to
match against, so they fire only when a human types the slash command — even
though CLAUDE.md's own dispatch prompt tells agents that "for a large or
stubborn convergence, hand steps 3-5 to the `/allium-loop` skill".

### A3 — `grill` promises a trigger list that does not exist

> …or says any 'grill' trigger phrase.

The body lists no trigger phrases. The clause is circular: it tells the model to
fire when the user says something that fires it. Replace with the real phrases
("stress-test this", "poke holes in this", "interrogate this design", "grill me
on this").

### A4 — `wrap-up`'s description states the wrong step order

> Commits remaining changes, then takes one of three paths chosen by the user

The body's order is the reverse: Step 4 chooses the path, Step 5 runs retro,
Step 6 commits, Step 7 verifies. The choice precedes the commit, and it must —
retro's own behaviour depends on which action was chosen (on `done` it files
instead of editing, because nothing carries a commit off the worktree).

The description also omits Step 7 entirely. The verify command is the one thing
CLAUDE.md calls out as load-bearing on this path, and Step 7 is where it runs.

### A5 — `learnings`' description omits deleting

Description: "query, rate, and record entries". The body has a "Deleting stale
entries" section, and `delete_learning` is one of the four tools it covers.

### A6 — `summarize`'s description omits its sub-step role

Step 4 branches on whether the skill was invoked standalone or as a sub-step of
another skill. The description describes only the standalone case.

### A7 — Nothing tests any skill's description

`src/setup/plugins.rs` asserts skill *body* content heavily (over twenty
`contains` tests via `skill_body`). No test reads frontmatter. A description can
drift arbitrarily far from its body with a green suite.

Adjacent gap in the same file: `plugin_embeds_required_files` lists seven skill
files and omits `skills/retro/SKILL.md` — the only shipped skill not guarded by
that test.

### A8 — `brainstorm-features` opens with filler

"This skill should be used when the user asks to…" — five words before the first
piece of information. Every other description in the repo leads with the verb.

## B. Skill body accuracy (found while auditing descriptions)

### B1 — `allium-weed-loop` weeds 3 of 15 specs

`.claude/skills/allium-weed-loop/prompt.md`:

> The specs are split across three files:
> - `docs/specs/core.allium` …
> - `docs/specs/tasks.allium` …
> - `docs/specs/epics.allium` …

`docs/specs/` holds fifteen. The same three-file list is baked into the literal
prompt handed to the weed subagent, so twelve specs — including
`dispatch.allium`, `feeds.allium`, `learnings.allium` and `mcp-task-tools.allium`
— are never checked. The loop can report "SPEC ALIGNED" while most of the spec
tree is unexamined.

(This matches archived knowledge-base entry #316.)

### B2 — `allium-weed-loop` has an undeclared plugin dependency

It writes `.claude/ralph-loop.local.md` and emits `<promise>SPEC ALIGNED</promise>`.
Both only mean anything with the `ralph-loop` plugin installed. Neither the
description nor the body says so; without the plugin the skill writes a state
file and stops.

## C. MCP tool descriptions

### C1 — `set_verify_command` is factually wrong (blocker)

> The command is injected into future agent prompts as a mandatory pre-completion check.

It is not injected into any prompt. `fetch_verify_command`'s own doc comment
says so directly: "No prompt builder reads it, so this has no caller on a
dispatch path". CLAUDE.md's "Verify Command" section agrees — the command
reaches the agent through `get_task`'s "Verify command" line and the `wrap_up`
response's reminder, and explicitly "never appears in the dispatch prompt".

An agent that believes this description will not look for the command on either
surface that actually carries it.

### C2 — `update_task`'s field list is stale and incomplete

> Update a task's status, sub_status, title, description, repo_path, plan, and/or PR fields.

Missing: `tag`, `epic_id`, `sort_order`, `base_branch`, `wrap_up_mode`,
`auto_run_plan`, `phoenix`. That is seven of the fifteen accepted fields.

"PR fields" is also the old name. The pair is now `url` / `url_type`, and
`url_type` covers `issue`, `security_alert` and `other` as well as `pr`.

### C3 — `get_task` says only "Get details about a task"

Five words, for the tool the `/wrap-up` skill depends on for three separate
values (`Base branch:`, `Verify command:`, `Wrap-up mode:`), each rendered only
when set.

Knowledge-base entry #552 records the concrete failure: agents read the response
as JSON and look for snake_case fields that do not exist. The description is the
right place to say the response is labelled prose lines and that an absent line
means an unset field.

### C4 — `list_tasks` describes the old URL output

> Output includes PR URL and plan goal when available.

The output renders the url under its own type label, so a security-alert task
prints `Security alert: <url>`, not `PR: <url>`. An agent scanning for "PR"
misses it.

### C5 — `subscribe_to_task` cites internal function names

> Delivery is a one-shot tmux nudge (write_message_file + notify_tmux).

An agent cannot act on either name. This is exactly the citation shape
`check-doc-symbols.sh` rejects in `docs/` — but that checker does not scan
`src/`, so an MCP description can carry a stale symbol name indefinitely with
nothing to catch it.

### C6 — `record_learning` duplicates the `/learnings` skill body

Roughly 200 words of recording policy — the "could you write a failing check"
test, the no-symbol-names rule, the `procedural`-needs-a-boundary rule — appear
in full in both the tool description and `plugin/skills/learnings/SKILL.md`.
Two copies of a policy that must now be edited in lockstep by hand, with no test
comparing them.

### C7 — `create_task` leaks transport detail

> Caller identity is provided by the dispatch HTTP transport (X-Caller-Task-Id for
> dispatched agents, X-Caller-Kind: session for non-dispatched sessions)

The agent cannot set, read or change these headers. The only actionable part is
the clause that follows: "you do NOT pass a caller_task_id argument."

### C8 — `create_epic` omits sub-epics

Its schema accepts `parent_epic_id`, and `update_epic`'s description does mention
re-parenting. `create_epic`'s says only "Create a new epic on the kanban board."

### C9 — Nothing tests MCP descriptions either

Same gap as A7, one layer down. `mcp_tools!` and `mcp_args!` generate the
description strings; no test asserts anything about their content.

---

## Deployment note (not a finding)

MCP tool descriptions reach an agent from the **running** dispatch binary, not
from the worktree. This session's server still advertises the pre-`e7fff9f9`
`update_task` status enum (`backlog`/`running`/`review`, with "Setting done is
not allowed via MCP"), which the source no longer says. Any description fix
lands for agents only after the server is rebuilt and restarted.

---

## Resolution

All nineteen findings are fixed. `.claude/skills/lint.md` was deleted rather
than relocated, at the user's direction.

The recurrence gap (A7/C9) is closed by tests rather than by review, and the
ones that can be derived from a machine-readable source are:

| Guard | Lives in | Derived from |
|---|---|---|
| every skill declares a `name:` matching its directory | `src/setup/plugins.rs` | the embedded `skills/` directory listing |
| every skill description says when to invoke it | `src/setup/plugins.rs` | same |
| `update_task`'s description names every field it accepts | `src/mcp/handlers/tests/mod.rs` | the generated input schema |
| `list_tasks`' description names every url label | `src/mcp/handlers/tests/mod.rs` | `UrlType::ALL` |
| no tool description cites an internal symbol | `src/mcp/handlers/tests/mod.rs` | tool names + declared argument names |
| no loose `.md` masquerades as a repo skill | `tests/repo_skills.rs` | the `.claude/skills/` listing |
| `allium-weed-loop` does not weed a subset of the specs | `tests/repo_skills.rs` | the `docs/specs/` listing |

Four are fixed-string assertions, because the fact has no machine-readable
source: wrap-up's step order, grill's trigger phrases, learnings' four verbs,
summarize's sub-step role, and the two `set_verify_command` /
`get_task`/`create_epic`/`record_learning`/`create_task` description guarantees.

Spec changes: a new "Tool descriptions" preamble in `mcp-task-tools.allium`
setting the standard for the surface, plus per-rule guarantees on
`UpdateTaskViaMcp`, `GetTaskViaMcp`, `ListTasksViaMcp` and
`SetVerifyCommandViaMcp`; and in `learnings.allium`, a record of what the
`record_learning` description carries versus what the `/learnings` skill owns,
now that the duplication is cut.
