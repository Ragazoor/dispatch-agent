# git fetch/push over an SSH remote fail under the sandbox despite allowedDomains

## Investigation

Reported from task #4287: this repo's `origin` remote is SSH
(`git@gh-ragazoor:Ragazoor/dispatch-tui.git`, a personal `~/.ssh/config` alias),
and `git fetch origin main` under the sandbox failed with a `socat`/gateway
error even though `github.com`/`api.github.com` are in
`sandbox.network.allowedDomains`.

Root cause: `allowedDomains` only matches HTTP(S) requests against a domain
name. An SSH remote is a raw TCP connection to a host (frequently an alias
with no resolvable relationship to `github.com` at the network layer), so it
is blocked by the sandbox regardless of what's in `allowedDomains` — this is
the same class of gap as task #4287's `gh` keyring finding (AF_UNIX sockets
aren't domain traffic either), just at a different layer.

Confirmed `sandbox.excludedCommands` fully lifts the sandbox for a matching
invocation — not just the network layer, but also
`sandbox.credentials.files` (this repo denies reading `~/.ssh`) and the
filesystem/seccomp restrictions the Gradle-wrapper and `gh` entries already
rely on. That matters here because it cuts both ways: it's *necessary* (git
needs to read the SSH private key to authenticate, which the credential-deny
list otherwise blocks even once the network problem is fixed), and it's a
*real widening of exposure* (an unsandboxed `git fetch`/`git push` could in
principle be abused via e.g. `-c core.sshCommand=...` to do more than just
authenticate).

Considered whether dispatch could sidestep this by using HTTPS remotes
instead (already covered by the existing `allowedDomains` entries, no
sandbox change needed) — ruled out because dispatch worktrees are `git
worktree` children of the user's existing clone and inherit its `origin`
config; the SSH alias is the user's own environment choice
(`~/.ssh/config`), not something `dispatch setup`'s generated settings file
can or should override per task.

Presented the tradeoff to the user as three options: exclude `git fetch
*`/`git push *` broadly (same mechanism as Gradle/`gh`), exclude a narrower
`git fetch origin *`/`git push origin *` (marginally smaller blast radius,
but silently stops applying for any remote not literally named `origin`, and
doesn't reduce the credential-read exposure either way since that only
depends on the command matching at all), or leave it undone and keep
requiring `dangerouslyDisableSandbox`. Chosen: **exclude `git fetch
*`/`git push *`** — consistent with the existing Gradle/`gh` precedent, works
regardless of remote name, and git/gh are already hard runtime dependencies
of every dispatched task.

## Action

1. **Tests first**: extended `src/setup/statusline.rs`'s test module —
   updated `writes_sandbox_excluded_commands_for_gradle_wrapper`'s exact-list
   assertion to include the two new entries, and added
   `writes_sandbox_excluded_commands_for_git_ssh_remotes` asserting both are
   present.
2. **Implement**: added `"git fetch *"` and `"git push *"` to the
   `excludedCommands` array in `write_settings_file`
   (`src/setup/statusline.rs`).
3. **Spec**: added a `GitSshFetchPushExcludedFromSandbox` guarantee to
   `SandboxedAgentExecution` in `docs/specs/dispatch.allium`, documenting the
   mechanism, why it's a strictly bigger bypass than the `gh` entry, and why
   it was accepted anyway.
4. **CLAUDE.md**: updated the task #4287 note to describe the fix instead of
   only the symptom, including the caveat that a session running against a
   stale `~/.claude/dispatch-statusline.json` (not yet regenerated by
   `dispatch setup`) still hits the old failure.
5. Verified with `cargo test`.
